# Граф денег — восстановление финансовой структуры группы по транзакционной сети

Инструмент для AML-аналитика: по выгрузке исходящих переводов 81 клиента из дела (4 колена, 2 248 узлов) он строит граф и за **~4 секунды** выдаёт:

- **роль каждого узла** из словаря ТЗ с формальным правилом, уверенностью и обоснованием в числах;
- **ранжированный список «кого смотреть первым»** с разложением приоритета на понятные компоненты;
- **кластеры** с гипотезой о назначении каждого;
- **интерактивную схему сети**: направление потоков, роли и кластеры, поиск по gid, режим «связи узла» слева направо, карточка узла;
- **AI-ассистента**: вопрос на естественном языке («кто собирает деньги с этих пятерых?») → ответ по графу со ссылками на узлы.

Все выводы сформулированы как **признаки и гипотезы для проверки**, а не как утверждения о виновности.

## Быстрый старт

Нужен Python ≥ 3.10. Интернет не требуется (только для опционального LLM).

```bash
pip install -r requirements.txt
python run.py            # data/*.parquet → out/  (≈4 с)
```

Потом откройте `out/index.html` в браузере — это один самодостаточный файл, Cytoscape.js вшит в него, работает офлайн.

С AI-ассистентом:

```bash
python serve.py                                  # http://localhost:8000, офлайн-режим ассистента
OPENAI_API_KEY=sk-... python serve.py            # LLM-агент (модель по умолчанию gpt-5.4, меняется через OPENAI_MODEL)
# любая OpenAI-совместимая модель, в т.ч. локальная — данные не покидают контур банка:
OPENAI_BASE_URL=http://localhost:11434/v1 OPENAI_API_KEY=x OPENAI_MODEL=qwen2.5 python serve.py
```

Тесты (схема выгрузок, соответствие ролей правилам, отсутствие захардкоженных gid, цикл LLM-агента):

```bash
pip install pytest && python -m pytest -q        # 10 passed
```

`run.py` сам проверяет выгрузки по требованиям ТЗ и печатает результат:

```
  OK  nodes_roles.csv: 2248 строк (нужно 2248)
  OK  все роли из словаря ТЗ
  OK  evidence ≤200 символов и содержит числа
  OK  cluster_id каждого узла есть в clusters.csv
  OK  top_nodes.csv: 50 строк, отсортирован по приоритету
  ...
Готово за 4.2 с.
```

## Методика

### 1. Данные и их ограничения

До построения модели выгрузка проверяется (`moneygraph/load.py`): суммы и число переводов в `edges` сходятся с `transactions`, все gid из рёбер есть в `nodes`. Выяснилось, что `edge.depth = depth(src) + 1`: исходящие выгружены **у всех узлов 0–3 колена и ни у одного узла 4-го**. На этом построен учёт ограничений:

| Ограничение из ТЗ | Как учтено |
|-|-|
| Обрыв на 4-м колене: 444 узла без исходящих | признак `out_observed = depth < 4`. «Конечный получатель» на 4-м колене — только если **модель обрыва** даёт P(сток) ≥ 0.6, уверенность умножается на P(сток). Итог: 75 терминалов вместо наивных 444 |
| Только исходящие; вход — нижняя оценка | если узел отдал больше, чем получил в выборке, разница пришла извне. Она учитывается при атрибуции денег seed и попадает в запрос «входящие извне выборки» (184 узла) |
| Вход seed занижен | пропуск out/in у seed не используется ни для транзита, ни для приоритета. Для seed отдельное правило «seed-дроп» по исходящим |
| Порог 5 000 ₸ | дробление ниже порога не детектируется. Детектируется «несколько переводов одному получателю в один день» |
| 19 seed без рёбер, 12 только получают | 19 без рёбер — отдельный кластер 0 «нет данных» + запрос межбанка и наличных. Те, кто только получает, обрабатываются общими правилами (консолидатор/терминал) |
| 16 слабосвязных компонент | кластеризация не объединяет несвязные части; размер компоненты есть в признаках |
| Нет ground truth | роли — формальные правила с порогами, а не обученный классификатор. Соответствие правилам проверяется тестом |

### 2. Признаки узла (`moneygraph/features.py`)

| Признак | Смысл |
|-|-|
| `in_deg / out_deg`, `in_kzt / out_kzt`, `in_tx / out_tx` | разные плательщики/получатели, суммы, число переводов (сумма и количество — разные сигналы) |
| `pass_through` | out/in — какая доля полученного ушла дальше |
| `seed_payers`, `seed_upstream` | сколько плательщиков — seed; от скольких разных seed деньги доходят до узла за ≤4 перевода |
| `seed_kzt_in`, `seed_share` | **пропорциональная атрибуция денег seed**: деньги на счёте обезличены, поэтому каждый исходящий перевод несёт ту же долю «денег фигурантов», что и весь доступный узлу объём. Доступный объём = max(вход, выход): невидимые внешние поступления разбавляют долю. Считается как неподвижная точка линейной системы, с учётом циклов |
| `pagerank` (вес = ₸), `betweenness` (направленный) | куда стекаются деньги и кто стоит «между» |
| `key_links` | сколько прямых контрагентов сами являются ключевыми узлами (хаб, консолидатор или распределитель) |
| `fast_in_share`, `lag_median_days` | **сквозной транзит**: FIFO-сопоставление поступлений и списаний — какая доля полученного ушла дальше за ≤2 дня |
| `sync_payers_max` | **синхронный сбор**: максимум разных плательщиков в один день |
| `repeated_routes` | **устойчивые маршруты A→узел→B**: пересылка в пределах 2 дней, повторённая в ≥2 разные даты |
| `split_days` | **дробление**: дни с ≥2 переводами одному получателю |
| `n_return_cycles` | **возвратные потоки**: простые циклы длиной ≤6, согласованные по датам (деньги могли пройти круг). Таких 355 из 1 541 |
| `anomaly` | **аномалия относительно колена**: признак в топ-1% своего колена при существенной величине |
| `p_forward` | вероятность, что узел передаёт деньги дальше (для 4-го колена — по модели обрыва) |

### 3. Модель обрыва 4-го колена (`moneygraph/truncation.py`)

Наивное правило «out_deg = 0 ⇒ сток» даёт 444 ложных конечных получателя. У узлов 1–3 колена исходящие наблюдаемы, поэтому на них можно **обучиться**. Логистическая регрессия предсказывает «передаёт ли узел деньги дальше» **только по признакам входящей стороны** — у 4-го колена они наблюдаются так же. Признаки: сумма, число плательщиков и поступлений, крупнейшее поступление, число дней с поступлениями, день последнего поступления, доля входа от веерных отправителей, доля плательщиков-seed.

- обучение: 1 723 не-seed узла 1–3 колена, доля стоков 63%;
- **ROC-AUC 0.72** на 5-кратной кросс-валидации; коэффициенты выводятся в отчёт и во вкладку «Методика»;
- из 444 обрезанных узлов ожидаемо настоящих стоков ≈ 267; вероятные стоки (P ≥ 0.6) с существенным входом становятся терминалами с пониженной уверенностью. У остальных роль «периферия» с флагом `обрыв_4_колена`, а если вход существенный — запрос «исходящие 5-го колена».

Пример: `100000003985389100` — 16 поступлений от одного плательщика, **P(передаёт дальше) = 0.99**. Узел похож на транзитный счёт, наивно он был бы «стоком».

### 4. Роли: формальные правила (`moneygraph/roles.py`, пороги в `moneygraph/config.py`)

Правила проверяются **по порядку сверху вниз**, основной становится первая выполненная роль. Структурная роль важнее потоковой: узел, который собрал от 6 плательщиков и ничего не отдал, — консолидатор, а «конечный получатель» сохраняется в `role_secondary`.

| Роль | Правило (все пороги — в `config.py`) | Узлов |
|-|-|-|
| **coordinator** | ≥5 плательщиков **и** ≥10 получателей (хаб) **и** ≥5 прямых связей с другими ключевыми узлами — узел связывает несколько контуров, а не просто крупный счёт | 13 |
| **consolidator** | ≥4 разных плательщика (или ≥3, из них ≥2 seed) и плательщиков ≥ получателей; либо хаб, где сбор доминирует | 63 |
| **distributor** | ≥10 получателей и получателей ≥3× плательщиков; либо хаб, где раздача доминирует | 48 |
| **transit** | не seed, исходящие наблюдаемы; отдал 80–120% полученного **или** ≥60% полученного ушло за ≤2 дня (при пропуске 0.5–2.0); через узел прошло ≥20 тыс ₸. Для seed: переправил ≥100 тыс ₸ не более чем 9 получателям | 92 |
| **terminal** | исходящие наблюдаемы, дальше ушло ≤10%; получил ≥100 тыс ₸, или от ≥2 плательщиков, или ≥3 поступлений. 4-е колено — только при P(сток) ≥ 0.6 | 500 |
| **peripheral** | ни одно правило не выполнено | 1 532 |

**role_score** = 0.5 + 0.5 × сила признака: сам факт прохождения порога даёт уверенность ≥0.5, насколько узел превышает порог — остальное. Сила признака — прозрачная формула с насыщением по лог-шкале. Например, для консолидатора: 0.5 × (число плательщиков, 3→20) + 0.25 × доля входящих связей + 0.25 × (seed-плательщиков / 3). Для периферии уверенность тем выше, чем дальше узел от любого порога. У обрезанных узлов она ниже, у 19 seed без переводов равна 0.3.

**evidence** (≤200 символов, всегда с числами), например:
- `Хаб: 19 плательщиков → 61 получателей; вход 1.8 млн ₸, выход 5 млн ₸; связан с 19 ключевыми узлами; возвратных циклов: 96`
- `Сбор от 7 плательщиков (seed: 6): 393 тыс ₸; дальше ушло 13% (1 получ.); деньги 11 seed доходят до узла`
- `4-е колено, исходящие не выгружены; модель: P(сток)=0.66; получил 1.8 млн ₸ от 1`

### 5. Приоритет (`moneygraph/priority.py`)

```
priority = 0.30·роль + 0.20·связь с фигурантами + 0.20·оборот + 0.15·положение в сети + 0.15·паттерны
```

| Компонента (0..1) | Как считается |
|-|-|
| роль | вес роли × role_score. Веса: координатор 1.0, консолидатор 0.9, распределитель 0.75, терминал 0.6, транзит 0.55, периферия 0.1 |
| связь с фигурантами | ½·(сколько seed доходят до узла, 1→12) + ½·(деньги seed по атрибуции, 10 тыс→2 млн ₸), лог-шкала |
| оборот | max(вход, выход), 50 тыс → 10 млн ₸, лог-шкала |
| положение в сети | ½·процентиль PageRank по ₸ + ½·процентиль betweenness |
| паттерны | число флагов / 4: транзит ≤2 дн, синхронный сбор, возвратные циклы, аномалия колена, повторяющиеся маршруты, дробление |

Затем seed × 0.85: они уже известны правоохранителям, и при равных признаках выше ставятся **новые** узлы. Итог делится на максимум. В топ-20 — 17 новых узлов. Поле `why` в `top_nodes.csv` собирается из тех же чисел: роль и обоснование, три главных фактора, признаки, что проверить.

### 6. Кластеры (`moneygraph/clusters.py`)

- Louvain на **неориентированной** проекции (оговорка ТЗ: направление здесь сознательно не учитывается, кластер отвечает на вопрос «кто с кем связан деньгами», а направление учтено в ролях). Вес ребра = log(1 + сумма/5000): крупные переводы важнее, но не подавляют структуру. Модулярность **0.80**, 48 кластеров, в 9 из них больше одного seed.
- **Устойчивость**: Louvain перезапускается ещё 10 раз с другими random seed. Для кластера считается средний Jaccard с лучшим совпадением: 1.0 — кластер воспроизводится всегда.
- **Гипотеза** выводится из состава ролей по правилам-архетипам: *ядро* (есть координатор), *контур сбора* (консолидатор, питаемый ≥2 seed), *веерные выплаты*, *транзитная цепочка*, *граница выборки* (≥50% обрезано 4-м коленом), *периферия*. В текст подставляются ключевой узел и числа.

### 7. Устойчивость сети (`moneygraph/resilience.py`)

Что будет, если заблокировать N узлов. Для одинакового N сравниваются четыре стратегии: наш топ, топ по обороту, seed с наибольшими исходящими (текущая практика — блокировать известных курьеров) и случайные узлы.

| Блокировка 20 узлов | Гигантская компонента | Фрагментов ≥3 узлов | Доля оборота в ней |
|-|-|-|-|
| без блокировок | 1 877 | 14 | 94% |
| **наш топ** | **1 311** | **58** | **55%** |
| топ по обороту | 1 286 | 58 | 46% |
| 20 seed с макс. исходящими | 1 569 | 32 | 71% |
| 20 случайных | 1 844 | 15 | 92% |

Вывод: переход от блокировки курьеров к нашему топу разрушает сеть в разы сильнее. Честная оговорка: топ по обороту даёт сопоставимый эффект, потому что крупные хабы входят и в наш топ. Разница в том, что наш список **объясним ролями** и включает точки консолидации с небольшим оборотом, но деньгами многих seed.

### 9. AI-ассистент (`moneygraph/assistant.py`, `serve.py`)

Агент на OpenAI Chat Completions с **function calling** и 8 инструментами над графом:

| Инструмент | Что делает |
|-|-|
| `node_card` | роль, обоснование, суммы, главные плательщики и получатели, пробелы в данных |
| `common_downstream` | кто собирает деньги с нескольких узлов: общие получатели, прямые и через ≤3 перевода |
| `trace` | откуда пришли / куда ушли деньги, 1–3 шага |
| `path_between` | кратчайшая денежная цепочка между двумя узлами в обе стороны |
| `top_nodes`, `cluster_info`, `data_gaps`, `network_summary` | топ с фильтрами, кластер, запросы данных, сводка |

- LLM видит только то, что вернули инструменты. Системный промпт запрещает выдумывать gid и суммы и требует формулировок «признаки/гипотеза».
- Без ключа тот же набор инструментов вызывается **офлайн-разбором** типовых вопросов, так что демо не зависит от интернета. При ошибке API ассистент автоматически переключается на офлайн-режим.
- `OPENAI_BASE_URL` подключает любую OpenAI-совместимую модель, в том числе локальную (Ollama, vLLM): данные не покидают контур банка.
- В ответе gid кликабельны: клик открывает карточку и показывает узел на схеме.
- Цикл агента покрыт тестом с фейковым OpenAI-совместимым сервером.

| 4 | 100000000437046100 | coordinator | 0.980 | Хаб: 9 → 42; вход 1.1 млн ₸, выход 7.6 млн ₸; связан с 15 ключевыми узлами; возвратных циклов: 45 |
| 5 | 100000003684369100 | coordinator (seed) | 0.949 | Хаб: 24 плательщика (seed: 1) → 62 получателя; вход 3.8 млн ₸, выход 8.6 млн ₸ |

Полный список — `out/top_nodes.csv`, сводка — `out/report.md`.

**Главная гипотеза.** Над нижним уровнем (seed) видно **ядро из хабов-координаторов** (кластер 1: 352 узла, 5 координаторов, 42 узла в возвратных циклах). Хабы получают деньги извне выборки (выход в 1.1–26 раз больше видимого в выборке входа), быстро пропускают их (до 100% за ≤2 дня) и сходятся на **консолидаторах второго уровня**. Так, `100000003115284100` получает от 8 плательщиков, 6 из которых — координаторы (2 из них seed). Такой профиль похож на сеть P2P-обменных счетов или «прокладок». Это гипотеза для проверки, а не вывод.

## Сценарий демо (5 минут)

1. `python run.py` — пересчёт за ~4 с, 10 проверок ТЗ в выводе.
2. `python serve.py` → обзор сети: цвет по ролям, затем по кластерам, вкладка «Кластеры».
3. **Узел #1 `100000008603629100` — координатор.** Правило: ≥5 плательщиков (у него 19) и ≥10 получателей (61) и ≥5 связей с ключевыми узлами (19). Разложение приоритета в карточке, флаги: 100% полученного ушло ≤2 дней, 96 возвратных циклов.
4. **Узел #2 `100000003115284100` — консолидатор.** «Связи узла»: слева 8 плательщиков, из них 6 координаторов (2 — seed), справа уходит лишь 24%. Правило: ≥4 плательщика (8), плательщиков ≥ получателей (8 ≥ 2).
5. **Обрыв графа:** `100000003985389100` — 4-е колено, 16 поступлений, модель: P(передаёт дальше) = 0.99, поэтому не «сток», а запрос исходящих 5-го колена.
6. Ассистент: «Кто собирает деньги с `100000000343175100, 100000000331309100, 100000000437046100`?» → консолидатор #2 получает от всех трёх.
7. «Устойчивость»: блокировка 20 узлов топа → гигантская компонента 1 877 → 1 311, фрагментов 14 → 58, против 1 569 при блокировке 20 seed.

## Ограничения подхода

- Роли — правила с порогами, выбранными по распределениям этих данных. На других выгрузках пороги нужно перепроверить (все они в `config.py`).
- Атрибуция денег seed пропорциональная: деньги обезличены, конкретный рубль не прослеживается.
- Вход узлов — нижняя оценка, поэтому пропуск out/in у хабов завышен. Это отражено в тексте обоснования и в запросах данных.
- Модель обрыва обучена на коленах 1–3. Узлы 4-го колена по построению отличаются (приходят только от 3-го колена), это сдвиг распределения. AUC 0.72 — полезный, но не решающий сигнал.
- Louvain недетерминирован. Seed зафиксирован, а устойчивость кластера выводится явно: кластер 1 (0.55) менее стабилен, чем большинство (медиана 1.0).
- Дробление ниже 5 000 ₸, межбанковские переводы и наличные не видны в принципе.

## Масштабирование до ~1 млн узлов

| Шаг | Сейчас (2 248 узлов) | При ~1 млн узлов |
|-|-|-|
| Хранение и загрузка | pandas + parquet | Polars / DuckDB, партиционированный parquet, выгрузка обходом на стороне хранилища |
| Граф | networkx | igraph / graph-tool (C), либо GraphFrames / Neo4j GDS для распределённого расчёта |
| Степени, суммы, пропуск, время | pandas | те же group-by в DuckDB / Spark — линейно по числу транзакций |
| Атрибуция денег seed | итерации на `scipy.sparse` | уже разрежённая: итерация = SpMV, O(рёбер) |
| Seed выше по потоку | BFS от каждого seed | multi-source BFS с битовыми масками seed или HyperLogLog-скетчи |
| PageRank | networkx | igraph / Spark GraphFrames |
| Betweenness | точная, O(V·E) | приближённая по выборке источников (k-sampling) или только внутри кандидатов |
| Циклы | `simple_cycles(≤6)` на всём графе | только внутри нетривиальных SCC и вокруг кандидатов с ограничением длины и времени |
| Кластеры | Louvain | Leiden (igraph / cuGraph), иерархическая детализация по запросу |
| Модель обрыва | логрегрессия sklearn | та же модель, обучение на выборке; инференс батчами |
| Экран | весь граф в браузере | в браузер уходит не весь граф, а срез: топ-N, кластер, эго-граф узла с сервера; WebGL-рендер (sigma.js) |
| Роли и приоритет | правила на pandas | те же правила как SQL/векторные выражения — линейно |

Интерфейс данных пайплайна от этого не меняется: те же три parquet на входе и те же три CSV на выходе.

## Приватность и этика

- Работа только с обезличенными gid. Никаких ФИО, ИИН и внешнего обогащения.
- Всё считается локально. Внешний вызов возможен только к LLM API, и только если ключ задан явно. Через `OPENAI_BASE_URL` можно использовать локальную модель.
- Формулировки — «признаки», «гипотеза», «проверить», а не утверждения о виновности.
